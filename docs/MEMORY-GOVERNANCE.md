# 记忆治理方案（长期使用）

- 目标：记忆长期增长时，**检索仍然准、摘要仍然有用、历史仍然可追溯**
- 前提：不删除历史（Markdown 是资产），只做分层与合并

---

## 一、先算账：真正的瓶颈不是存储

按当前节奏估算：

| 项 | 数值 |
|---|---|
| 每条记忆正文平均 | ~1.2 KB（11 条 = 13.5 KB） |
| 假设每天 5 个任务 × 每任务 3 条 | 15 条/天 ≈ 5,500 条/年 |
| 一年正文 | ~6.6 MB |
| 索引（trigram，约 1.5–2×） | ~13 MB |
| 十年总量 | ~200 MB |

结论：**存储永远不是问题。** 真正的约束有两个：

1. **DIGEST 必须 ≤ 4 KB** —— 而记忆在无限增长
2. **检索精度随噪音下降** —— 重复、过时、互相矛盾的条目会挤占结果

所以治理的核心不是"压缩存储"，而是**管理工作集（working set）**。

---

## 二、三层结构：hot / warm / cold

| 层 | 内容 | 数量目标 | 进入检索 | 进入摘要 |
|---|---|---|---|---|
| **hot** | 当前有效的核心记忆 | ≤ 150 条 | ✅ 默认 | ✅ |
| **warm** | 仍有效但非核心 | 不限 | ✅ 默认 | ❌ |
| **cold** | 已归档（过时/被合并/低频） | 不限 | 需 `--all` | ❌ |

判定方式不是人工打标签，而是**访问 + 衰减评分**自动决定：

```
score = confidence_weight × exp(-days_since_use / 180) × (1 + ln(1 + uses))
```

- `confidence_weight`：high=1.0 / medium=0.6 / low=0.3
- `uses`：被 `mem_get` / `mem_search` 命中的次数
- 连续 180 天未被使用且 score 低于阈值 → 进入 review 队列 → 降为 cold

**关键**：cold 不是删除，文件移到 `archive/`，`mem_search --all` 仍可查到。

## 三、五个机制

### 1. 写入侧：挡住噪音

| 措施 | 现状 | 补充 |
|---|---|---|
| 精确去重（正文哈希） | ✅ 已有 | — |
| **近重复检测**（trigram Jaccard ≥ 0.8） | ❌ | 写入时提示"疑似重复：<id>"，由调用方决定合并还是另写 |
| **写预算** | 规范（每任务 ≤3 条） | 可硬化为每日每 agent 配额，超限拒绝并提示 |
| **槽位化事实**：`subject` + `claim` | ❌ | facts/preferences 增加可选 `subject`，同 subject 的新事实自动 supersede 旧的 |

槽位化是解决"记忆互相矛盾"的关键：没有它，"端口是 8001"和"端口改成了 8002"只能靠人肉发现冲突。

### 2. 使用侧：记录谁在被用

- `mem_get` / `mem_search` 命中时更新 `uses`、`last_used_at`
- 这是衰减评分的输入，也是"哪些记忆该进摘要"的依据
- 成本：一次索引 UPDATE，可接受

### 3. 维护侧：定期体检而不是等它烂

`memhub review` 输出四类问题：

| 类别 | 判定 | 建议动作 |
|---|---|---|
| 重复 | 相似度 ≥ 0.8 | 合并（保留信息更全的一条） |
| 过期 | `review_at` 已过，或 180 天未用 | 复核 / 归档 |
| 冲突 | 同 `subject` 多条有效 | 保留新的，旧的 supersede |
| 孤立 | 没有任何 `links` 且 90 天未用 | 归档候选 |

默认只报告，`--apply` 才动手；**归档不删除**。

### 4. 合并侧：episodes 自动，决策/事实需批准

| 类型 | 策略 |
|---|---|
| `episodes` | 可自动合并：同月同项目的会话沉淀 → 一条月度纪要，原文归档 |
| `facts` / `preferences` | 只允许"同 subject 覆盖"，不合并不同主题 |
| `decisions` / `entities` | **禁止自动合并**，必须人工确认（合并会丢理由与备选） |

合并操作本身也走 `supersede` 链：新纪要 `supersedes` 多条旧记忆，旧条目标记 superseded + `valid_to`。**审计链不断，历史仍可查。**

### 5. 审计侧：合并也要留痕

- 合并产生的记忆必须带 `links: [{rel: consolidates, target: <旧 id>}]`
- `verify` 会校验链；被合并的旧条目保留在 cold
- 任何"这条记忆从哪来"的问题，都能顺着链回答

## 四、状态机（扩展）

```
active ──revise──► superseded
  │                    
  ├──archive──► archived ──gc(30d)──► 物理删除
  └──forget──► tombstoned
```

- `archived`：移入 `archive/`，默认不检索
- `superseded`：被修订或合并取代，保留可查
- 物理删除只发生在 `gc`，且默认 dry-run

## 五、自动化节奏

| 频率 | 任务 | 内容 |
|---|---|---|
| 每 6 小时 | `dsh sync`（已上线） | 刷新摘要 + 沉淀会话 |
| 每天 03:00 | `memhub review --report` | 生成待处理清单，不自动改 |
| 每周日 | `memhub consolidate --episodes` | 合并 90 天前的会话沉淀为月度纪要 |
| 每月 1 日 | `memhub archive --stale` | 归档 180 天未用且低分的记忆 |
| 每月 | `memhub health` | 输出增长、重复率、命中率、hot/warm/cold 分布 |

**只有第一项是全自动的**；其余三项默认只产出报告，人工确认后加 `--apply`。理由：合并与归档会改变"我记得什么"，这个决定不该完全交给脚本。

---

## 六、健康指标

`memhub health` 输出：

| 指标 | 健康范围 | 说明 |
|---|---|---|
| 总量 | 无上限 | 关注增长速度 |
| hot 占比 | 5–15% | 过高说明不收敛，过低说明丢了核心 |
| 重复率 | < 5% | 相似度 ≥0.8 的条目占比 |
| 30 天命中率 | > 40% | 被检索/读取过的记忆比例 |
| 平均置信度 | > 0.7 | 低置信度堆积说明写入草率 |
| 摘要利用率 | 20–60% | 摘要条数 / hot 条数，过高说明摘要在硬塞 |

## 七、分期实施

| 阶段 | 内容 | 工作量 | 验收 |
|---|---|---|---|
| **P1** | 访问计数 + 近重复检测 + `review` / `archive` / `health` | 3–4 h | 能列出重复与过期清单，归档可回滚 |
| **P2** | `subject` 槽位 + 冲突检测 + 自动 supersede | 2–3 h | 同 subject 新事实写入后旧事实失效 |
| **P3** | `consolidate`：episodes 月度合并（`--apply`） | 3 h | 10 条会话 → 1 条纪要，旧条目标 superseded |
| **P4** | 定时任务 + 指标看板 | 2 h | 周报自动产出 |

## 八、风险与取舍

| 风险 | 缓解 |
|---|---|
| 过度合并丢细节 | 合并默认关闭；decisions 禁止自动合并；原文进 cold 不删 |
| 衰减误伤重要记忆 | `pinned` 标记可豁免衰减；人工 review 兜底 |
| 人工成本太高 | 每周只看 10–20 条候选，其余全自动 |
| LLM 蒸馏引入错误 | 蒸馏产物一律 `confidence: low` + 带来源链接，人工确认后升级 |
| 指标好看但没用 | 以"换 agent 后是否需要重讲背景"作为终极指标，不看数字 |

---

## 九、不做的事

- 不做向量库（可解释优先；规模远未到需要）
- 不做自动删除（只归档）
- 不做跨设备同步（v1）
- 不做"记忆自动改代码"之类的自动执行
